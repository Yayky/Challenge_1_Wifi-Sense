The complete product flow

Radar input, room filtering, arming, and phone alerts are planned. The current application uses simulated positions. Diamonds are decisions; follow their labeled arrows.

Hold times come from current code. Full tracking of each missing person is still planned. Alert rules, sensor recovery, and delivery retries need design.
After any outcome, monitoring continues with the next reading until you stop the system. This includes an empty room, dashboard-only presence, and successful or failed alerts.

A held dot means the person may still be there. An empty display means no detected or held targets, not proof that nobody is physically present. The alert rule must still define cooldowns and whether inferred presence can trigger a notification.

What the repository runs today

Each browser connection gets its own simulator. Two moving dots disappear periodically; the server remembers only the first person when all detections disappear.

No real radar input, room filter, arm switch, or notifications yet. Holds use frame counts: roughly 15 seconds or 5 minutes at 10 updates per second.
Closing the connection ends that stream. The dashboard shows “disconnected” but leaves its last room display visible. Reload to start a new connection.

The optional WiFi-CSI experiment is also planned: two ESP32 boards → USB serial → signal analysis → comparison with radar → research results. It does not currently control alerts.
